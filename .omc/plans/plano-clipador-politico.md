## 1. Resumo do requisito

Sistema **CLI, sem interface visual**, que recebe o link de um vídeo do YouTube (inicialmente de canais ligados ao Partido Missão / MBL, com foco em Renan Santos) e produz automaticamente:

- Clipes longos **16:9** (5, 10, 15 min)
- Clipes curtos **9:16** (30s–1min30) com **reenquadramento seguindo rosto**
- **Legendas** estilizadas embutidas
- **Título, descrição e hashtags** gerados por IA
- **Thumbnail** gerada

Diferencial central pedido pelo usuário: a IA que escolhe os trechos e escreve os textos precisa de **contexto além da transcrição** — uma base de conhecimento sobre o movimento e a pessoa (pautas, posicionamentos, tom de voz, biografia) que ela consulta antes de decidir. Começa com 1 movimento/pessoa, arquitetura pensada para expandir depois.

## 2. Como o fluxo funciona ponta a ponta

```
[1] Ingest          → link do YouTube (ou arquivo local) entra no sistema
[2] Download         → vídeo + metadados oficiais baixados
[3] Transcrição      → áudio vira texto com timestamp por palavra + quem fala
[4] Seleção de trechos → LLM lê transcrição + KB do movimento, aponta os melhores recortes
[5] Reenquadramento  → cada recorte vertical é recortado seguindo o rosto de quem fala
[6] Legendas         → texto estilizado (efeito palavra-a-palavra) é queimado no vídeo
[7] Metadados        → LLM (com contexto da KB) escreve título, descrição, hashtags
[8] Thumbnail        → melhor frame do próprio recorte + composição gráfica
[9] Revisão editorial → checagem rápida de qualidade/factualidade antes de publicar
[10] Export           → arquivos finais 16:9 e 9:16 + metadados prontos para publicar
```

Cada etapa abaixo detalha **o que será usado** (categoria de tecnologia) e **por que é viável**, com base na pesquisa feita.

### [1] Ingest — entrada de vídeo

Dois adaptadores para o mesmo ponto de entrada:
- **Por URL do YouTube** (conveniência, canal público)
- **Por arquivo local** (upload do master, quando o time do movimento fornece o arquivo original em qualidade superior)

Ter os dois desde o início não é luxo: a pesquisa de risco legal (seção 5) mostra que baixar vídeo de terceiro via scraping é a parte juridicamente mais exposta do sistema. Se o conteúdo é do próprio movimento (o que é o caso aqui — Missão/MBL/Renan Santos), o caminho de arquivo local elimina essa exposição por completo e deve ser o caminho preferencial em produção; a URL fica como conveniência para prototipagem e para vídeos que só existem publicados.

**Ferramentas:** nenhuma lib externa — é um adaptador próprio (roteamento simples: URL vai pro downloader, arquivo local pula direto pra transcrição).

### [2] Download e metadados

- **yt-dlp** como ferramenta de download (padrão de facto, ainda funcional, mas hoje exige um runtime JS externo — Deno/Node — instalado ao lado por causa de mudanças anti-bot do YouTube de 2025/2026). Precisa rodar com atualização automática e tolerância a quebras periódicas; isolar atrás de uma interface própria para trocar de implementação sem afetar o resto do pipeline.
- **YouTube Data API v3** como fonte canônica de metadados oficiais (descrição completa, tags, thumbnail em alta, duração, licença) — reduz a necessidade de scraping para tudo que não é o arquivo de mídia em si.
- Captura de capítulos (do `--write-info-json` do yt-dlp, que já vem estruturado) como heurística inicial de possíveis cortes.
- Legendas automáticas do próprio YouTube tratadas como fallback de baixa qualidade; a transcrição real do sistema vem da etapa [3].
- **ffmpeg** faz o merge dos streams video-only + audio-only que o yt-dlp baixa separados em qualidade alta (sem ffmpeg, trava em ~720p).
- Alternativa se yt-dlp quebrar: `pytubefix` ou `youtubei.js` — mas sofrem o mesmo tipo de bloqueio (mesma API interna do YouTube por trás), então é diversificação, não redundância real.

### [3] Transcrição (ASR)

- **Whisper local (via faster-whisper/WhisperX)** como motor primário — roda self-hosted, boa qualidade em PT-BR, e WhisperX adiciona **alinhamento forçado por palavra** (timestamp de cada palavra individual, não só por frase) e **diarização** (via pyannote, integrada), essencial para saber quem fala quando há mais de uma pessoa no vídeo.
- Alternativa cloud (AssemblyAI/Deepgram/Google/Azure) fica como opção secundária para cenários sem GPU disponível ou para comparação de qualidade.
- O timestamp por palavra viabiliza tanto o efeito de legenda "karaokê" (etapa [6]) quanto o corte preciso de clipe (etapa [4]) sem depender do LLM inventar números.

### [4] Seleção de trechos por LLM (com contexto da base de conhecimento)

Esta é a etapa central do diferencial do produto. O LLM recebe:
- A transcrição com timestamps
- **A base de conhecimento do movimento/pessoa** (ver seção 3 — RAG/KB)
- Instruções de formato de saída estruturado (JSON com início/fim/justificativa/score)

O LLM aponta candidatos a clipe (curtos e longos) com base em critérios do tipo: gancho nos primeiros segundos, carga emocional/controvérsia, ideia que se sustenta sozinha sem contexto externo, alinhamento com pauta prioritária do movimento. Concorrentes como OpusClip usam abordagem parecida (transcrição + sinais multimodais + "virality score" 0–99 combinando força do gancho, fluxo emocional, valor percebido e alinhamento com tendência).

Mitigação de erro conhecida e necessária: **o LLM nunca inventa timestamp** — ele referencia índices/IDs de palavras já timestampadas pela transcrição (etapa [3]), e o corte final é ajustado programaticamente para cair em uma pausa de silêncio natural (evita cortar no meio de uma frase).

**Ferramentas:** Claude (Sonnet/Opus via API) com **structured output/schema** forçando o formato de resposta (JSON: `start_word_id`, `end_word_id`, `score`, `justificativa`) — evita parsing manual frágil de texto livre. Ajuste de corte pro silêncio mais próximo: análise simples de vale de energia/amplitude do áudio perto do word_id apontado.

### [5] Reenquadramento vertical (9:16) seguindo rosto

- **Detecção de rosto/pessoa**: MediaPipe Face Detection ou YOLO-face para localizar rostos em cada cena.
- **Active speaker detection** (saber QUEM está falando quando há mais de uma pessoa no frame): modelos como TalkNet-ASD, Light-ASD ou o mais recente LR-ASD — necessário porque Renan Santos frequentemente aparece em entrevistas/debates com mais de uma pessoa em quadro.
- **Estratégia de corte**: por cena (via detecção de mudança de cena), decidindo entre seguir o rosto (crop dinâmico) ou letterbox quando não há um sujeito claro; suavização de movimento para evitar "pulos" de câmera.
- **Renderização final**: ffmpeg aplicando o crop calculado frame a frame (ou pipeline Python/OpenCV alimentando ffmpeg), preservando qualidade.
- Existem projetos open-source recentes (2026) que já implementam essa combinação especificamente para este caso de uso (YOLO + tracking + MediaPipe + subject ranking), servindo como referência de viabilidade técnica direta — o problema está resolvido na literatura e na comunidade open-source, não é pesquisa em território desconhecido.

**Ferramentas:** `MediaPipe Face Detection`/`YOLOv8-face` (detecção de rosto) + `TalkNet-ASD` ou `Light-ASD` (quem está falando) + `PySceneDetect` (cortar por cena pra não recalcular frame a frame o tempo todo) + `OpenCV` (calcula a janela de crop, com interpolação/easing pra suavizar) + `ffmpeg` (aplica o crop e reencoda).

### [6] Legendas estilizadas

- Formato **ASS/SSA** (não SRT simples) para permitir estilo por palavra, cor de destaque, posicionamento — é o padrão usado pelas ferramentas comerciais para o efeito "palavra em destaque conforme é falada".
- Burn-in via filtro `subtitles` do ffmpeg (uma linha de comando, robusto para pipeline automatizado).
- Boas práticas identificadas: 4–6 palavras visíveis por vez, contraste de cor forte no destaque (ex: branco → amarelo).

**Ferramentas:** gerador de `.ass` próprio a partir do timestamp por palavra da etapa [3] + `ffmpeg -vf "ass=arquivo.ass"` pro burn-in.

### [7] Geração de título, descrição e hashtags (com contexto da KB)

Mesmo LLM/mesma chamada da etapa [4] ou etapa separada, mas sempre **com a base de conhecimento injetada** (ver seção 3) — é o que garante que o texto gerado reflita vocabulário, pautas e tom de voz reais do movimento, e não um texto genérico de "vídeo político qualquer". Inclui geração diferenciada por formato (um clipe de 30s no TikTok pede objetivo de copy diferente de um corte de 15min no YouTube).

**Ferramentas:** reusa a chamada Claude da etapa [4] (ou chamada separada reaproveitando o dossiê já em cache via prompt caching — barato, não multiplica custo por clipe).

### [8] Geração de thumbnail

Abordagem em camadas, por ordem de preferência (a mais segura primeiro):
1. **Extração do melhor frame do próprio clipe**: candidatos por I-frame/mudança de cena, pontuados por nitidez (Laplacian/Tenengrad) + rosto detectado com olhos abertos + expressão emocional forte. Sem risco de imagem alterada — é literalmente um frame real.
2. **Composição gráfica sobre o frame real**: faixa de cor, texto grande, elementos de marca — é o que ferramentas de política/notícia usam, previsível e seguro.
3. **Geração de imagem por IA (opcional)**: só para fundo/elementos gráficos, nunca para alterar rosto/expressão do candidato — mantém a thumbnail como representação fiel de um frame real.

**Ferramentas:** `ffmpeg select=eq(pict_type\,I)` (extrai candidatos por I-frame) + `OpenCV` (score de nitidez via variância de Laplaciano) + `MediaPipe` (olho aberto, rosto centralizado) + `Pillow` ou `ffmpeg drawtext` (composição de texto/faixa sobre o frame escolhido). Se usar geração de imagem: modelo de geração (ex: Nano Banana/Seedream) só no fundo.

### [9] Revisão editorial

O produto final é sempre um **corte de conteúdo real** — a imagem é o rosto e a fala verdadeiros do candidato, a legenda é a transcrição literal do que ele disse. Não há geração de mídia sintética nem alteração de imagem/fala, então não se aplica aqui a camada de compliance de "conteúdo gerado/alterado por IA" (rotulagem eleitoral, política de deepfake de plataforma etc.) — a IA participa só na escolha do trecho e na redação de título/descrição/hashtags, que é texto de apoio, não a peça em si.

Ainda assim, uma checagem editorial leve antes de publicar continua sendo boa prática (não é gate de compliance, é controle de qualidade): conferir se o corte não descontextualiza a fala e se o título/descrição batem com o que foi realmente dito.

**Ferramentas:** nenhuma — é etapa humana. Output do pipeline vai pra uma pasta de revisão antes de qualquer publicação.

### [10] Exportação

Arquivos finais nos dois formatos (16:9 longo, 9:16 curto) + pacote de metadados (título/descrição/hashtags/thumbnail) prontos para publicação manual ou upload assistido.

**Ferramentas:** `ffmpeg` (encode final, H.264, bitrate alvo) + estrutura de saída simples por clipe: vídeo + `.ass`/`.srt` + `.txt` (título/descrição/hashtags) + `thumbnail.png`.

## 3. Base de conhecimento (RAG) do movimento/pessoa

**Decisão de arquitetura: sem banco vetorial no início.** A pesquisa é conclusiva: bases de conhecimento de dezenas a poucas centenas de documentos curados (biografia, pautas, posicionamentos, glossário, discursos anteriores) são melhor servidas por injeção direta no prompt + busca em arquivo do que por um pipeline de embeddings/vetor — que só compensa em escala de milhões de documentos ou dados que mudam em tempo real, o que não é o caso aqui.

Arquitetura em duas camadas:
- **Camada 1 — dossiê "core" injetado no prompt, com cache de prompt.** Contém o que é usado em toda geração: traços de voz, pautas prioritárias, glossário, regras de compliance. Fica em cache (custo de leitura ~10% do normal), então gerar vários clipes do mesmo vídeo não multiplica custo proporcionalmente.
- **Camada 2 — arquivos markdown mais profundos**, organizados por tópico (padrão conhecido como "LLM knowledge base"/wiki), consultados sob demanda. Vantagem central para este caso: **é editável à mão por uma pessoa da equipe do movimento sem precisar reindexar nada** — corrigir um posicionamento errado é abrir um arquivo e editar, o que importa muito quando o custo de errar posicionamento político é reputacional.

Conteúdo sugerido da base (estrutura conceitual, não literal de pastas):
- Perfil de voz (traços de comunicação, com o que **não é** o tom do movimento também explícito)
- Pautas prioritárias e posicionamento por tema
- Biografia e histórico de Renan Santos / lideranças da Missão
- Glossário (grafia de nomes próprios, siglas, termos que o movimento usa/evita)
- Exemplos de títulos/descrições que já performaram bem (o ativo de maior alavancagem — mas precisa de revisão periódica para não "congelar" um tom antigo)
- Temas sensíveis / onde a pessoa não se posiciona ou se posiciona com nuance

Se a base crescer muito no futuro (múltiplos movimentos, muito material histórico), a migração para um banco vetorial leve (Chroma ou LanceDB) é um passo isolado, não um redesenho — a arquitetura em camadas já separa "o que sempre entra no prompt" de "o que é consultado por tópico".

**Ferramentas:** arquivos `.md` versionados em git, organizados por tópico. Camada 1 injetada direto no prompt (prompt caching automático da Claude API por prefixo). Camada 2 buscada por grep simples; se crescer, `SQLite FTS5` (full-text search) sem precisar de banco vetorial.

## 5. Riscos e mitigações

| Risco | Detalhe | Mitigação |
|---|---|---|
| **Bloqueio técnico de download** | YouTube endureceu proteção anti-bot (SABR, PO Tokens); IPs de datacenter são bloqueados com mais frequência; contas usadas intensamente com yt-dlp podem ser banidas | Preferir ingest por arquivo local quando possível (é conteúdo do próprio movimento); isolar downloader atrás de interface trocável; nunca usar conta principal para cookies |
| **Direito autoral / republicação de conteúdo de terceiro** | Baixar e recortar vídeo de canal de terceiro para republicar em outra rede normalmente exige autorização do titular; ToS do YouTube proíbe download automatizado independente do uso | Como o conteúdo é do próprio movimento (Missão/MBL), obter autorização/acesso direto ao material é o caminho correto — elimina a maior parte do risco. Tratar como bloqueador de produto, não detalhe técnico |
| **Descontextualização de fala real** | Cortar um trecho fora do contexto pode mudar o sentido do que foi dito, mesmo sem nenhuma alteração de mídia | Critério de seleção do LLM prioriza trechos que se sustentam sozinhos; checagem editorial leve antes de publicar |
| **Qualidade do reenquadramento com múltiplos falantes** | Troca de quem fala em entrevista/debate é o cenário mais difícil de reenquadrar bem | Active speaker detection dedicado (não só detecção de rosto) + estratégia de split-screen/crossfade como fallback quando a detecção não é confiável |
| **Alucinação do LLM na seleção de trechos** | LLM pode "inventar" timestamp ou cortar no meio de uma frase | Corte sempre referenciado a timestamps reais da transcrição, nunca gerado livremente pelo LLM; ajuste automático para cair em pausa de silêncio |
| **Base de conhecimento desatualizada** | Posicionamento político muda; exemplos de título "engessam" um tom antigo se não forem revisados | Ciclo de revisão periódica da base como parte do processo, não só na criação inicial |
